## 用語（正式名称・概要）── デッキ内で初出時に必ず提示

- **SFT（Supervised Fine-Tuning／教師ありファインチューニング）**: 入力→正解出力のペアでお手本どおりに答える振る舞いを教える学習。
- **LoRA（Low-Rank Adaptation）**: 全パラメータでなく小さな差分行列だけ学習する省メモリ手法。QLoRAは4bit量子化と併用版。
- **トークン / EOS（End Of Sequence／系列終端トークン）**: 文章を区切る最小単位がトークン。EOSは「ここで応答終わり」を示す特別なトークン。**これが壊れると生成が止まらない**（前回の崩壊の正体）。
- **GRPO（Group Relative Policy Optimization／グループ相対方策最適化）**: 強化学習(RL)の一種。同じ問いに複数の回答を生成し、相対的に良い回答を強める。DeepSeek-R1で有名。critic不要でPPOより軽い。
- **RLVR（Reinforcement Learning with Verifiable Rewards／検証可能報酬による強化学習）**: 正解と機械的に照合して報酬を決めるGRPOの使い方。採点が一意なタスク（分類・抽出・数学）向き。
- **RAG（Retrieval-Augmented Generation／検索拡張生成）**: 外部文書を検索して回答に使う。知識をモデルの外に置ける（後編）。

## 評価指標の定義（最初に用意する）── 本シリーズの背骨

> **方針**: 学習前にこの指標群・合格閾値・評価セットを固定し、まず `base` を測る。閾値は例（タスクに合わせて調整）。

### A. モデル（分類・項目抽出）の指標と"使える"閾値
| 観点 | 指標 | 閾値（例） |
|---|---|---|
| 分類 | Accuracy / **Macro-F1**（クラス不均衡対策）/ 混同行列 | Macro-F1 ≥ 0.85 |
| 抽出 | **フィールド別F1**（正規化後の値一致）/ レコード単位 **Exact Match** | フィールドF1 ≥ 0.90, EM ≥ 0.80 |
| 形式 | **スキーマ妥当率**（有効JSON＋必須キー＋型） | 100% |
| 健全性 | 空応答/反復/無限ループ率 | **0%**（前回崩壊の再発防止） |
| 運用 | レイテンシ p50/p95、1,000件あたりコスト | 用途で設定 |

- 比較は **base vs SFT vs SFT+GRPO** を同一ホールドアウトで。
- GRPOの報酬は上記指標の一部（カテゴリ一致＋項目F1＋スキーマ妥当性）だが、**評価セットは報酬と分離**（reward hacking検出のため）。

### B. RAG（社内ドキュメントQ&A）の指標
| 段階 | 指標 | 閾値（例） |
|---|---|---|
| 検索 | **Recall@k / Hit@k**、MRR | Recall@5 ≥ 0.90 |
| 生成 | **忠実性(Faithfulness＝根拠に基づくか＝ハルシネーション無し)**、回答関連性、回答正確性(gold有り時) | 忠実性 ≥ 0.95 |
| 根拠 | 引用ソース正確率 | 用途で設定 |
| 健全性 | 文脈不足時に「分かりません」と言える率（金融では良い振る舞い） | — |
| 運用 | レイテンシ、コスト、Claudeへのエスカレーション率 | — |

- **金融では忠実性が最重要**（作話は事故）。ツールは RAGAS / Langfuse evaluator。LLM-as-judgeは前回の審判ノイズに注意し、検証可能な指標（Recall@k等）と併用。
- **eval-set を最初に用意**: 社内文書に対する gold回答＋gold出典 のセットを seed固定で先に作る。

## 第1回「作る」── なぜ失敗し、どう"動くもの"にしたか

**ねらい**: 前回の失敗を解剖し、評価ファースト＋検証可能報酬GRPOで「出力そのもの」を最適化する再設計を示し、base vs 学習後の定量比較で締める。
**山場**: 同一タスクで base → SFT → SFT+GRPO のスコアが、**最初に決めた閾値**に向かって階段状に上がるデモ（前回 −35%、今回は上がる）。

**S1 — タイトル** · 「ローカルLLMで金融特化モデルを作る（前編：作る）」
- サブ: 「Val lossが嘘をついた話と、その先」／🖼 通しアーク図を薄く背景に。

**S2 — 今日のゴール / 2回シリーズの位置づけ**
- 前編は「作る」、後編で「使う」。今日はアークの左2.5個分。🖼 4ビートの今日の範囲をハイライト。

**S3 — 通しアーク図** · 失敗 → 再設計 → 動くモデル → アプリ＆コストキャップ。

**S4 — 用語の整理（最低限）**
- SFT・LoRA・トークン/EOS・GRPO・RLVR を **正式名称＋一言** で。「この5語が分かれば今日はOK」。

**S5 — 目的とゴールの定義**
- 金融（リスク管理・FP・証券）特化の日本語ローカルLLMを、**ノーマルと比較できる形**で作る。
- 当初要件: 前処理→増強→学習→GRPO→評価のパイプライン／公開金融データ／base vs 学習後比較／可能な限りローカル。
- **そして"使える"の合格閾値を最初に決める**（Macro-F1・EM・スキーマ妥当率・ループ率0%…）。

**S6 — 【失敗の解剖①】最初の挑戦**
- Mac(MLX)で Qwen3-8B に **SFT（教師ありファインチューニング）＋LoRA**。構成: 公開金融データ＋ダミー問い合わせ→学習→Ollama→評価。🖼 旧パイプライン図。

**S7 — 【失敗の解剖②】学習指標は順調だった**
- Train/Val loss は綺麗に下降（Val 2.067 → 1.348）。「成功した」ように見えた。🖼 lossカーブ。

**S8 — 【失敗の解剖③】でも評価は壊滅**
- test評価: base 0.534 → FT 0.182（**−35%**）。2周目は **全件0点**、**EOS（系列終端トークン）崩壊**で無限ループ。🎬 出力が同じ段落を繰り返す/全件0のスクショ。

**S9 — 失敗から得た5つの罠**
- ①Val loss≠実用品質 ②LoRAでもEOSは壊れる ③連続学習≠分割学習(Adam reset) ④評価"全件0"トラップ（エラー文字列が0点集計）⑤**評価を最後に回したのが根本原因**。

**S10 — 【再設計】今回変える3点**
- (1) **評価ファースト**（指標・閾値・評価セットを最初に作る）(2) **検証可能報酬GRPO**で"出力"を直接最適化 (3) **クラウドで再現性確保**。NVIDIAエコシステムのローカル等価で組む。

**S11 — なぜGRPO×RLVRが効くか**
- **GRPO** を **RLVR（検証可能報酬）** で回すと、報酬が**フォーマット遵守とEOSを直接矯正** → 前回の弱点にそのまま刺さる。
- 実例: Qwen-1.5B + GRPO が競技数学AIMEで o1 相当に到達（"狭いタスク"なら小モデルでもフロンティア級）。

**S12 — 期待値の整理（正直スライド）**
- 汎用知能でSonnet級 → ✕（規模差）。**狭く定義したタスクでフロンティア級** → ○。だから用途を絞る。

**S13 — 題材選定: 問い合わせ分類・項目抽出**
- 答えが採点できる＝GRPOが映える＆比較が一目。対象アプリ想定の実務タスク（後編の伏線）。

**S14 — 【評価ファースト】"使える"を先に数値で定義する**
- 学習前に: (1)指標と合格閾値を決める (2)seed固定のホールドアウト評価セットを作る (3)**base を先に測ってベースライン確定**（＝超えるべき線）(4)毎学習をこの評価で判定。
- これが「ただやっただけ」を防ぐ ── 前回はここを最後に回して失敗した。

**S15 — 評価指標：分類・抽出（合格ライン）**
- 分類=Macro-F1、抽出=フィールドF1＋レコードEM、形式=スキーマ妥当率、健全性=ループ/空応答率0%、運用=レイテンシ/コスト。
- 閾値例を提示（Macro-F1≥0.85 / EM≥0.80 / スキーマ100% / ループ0%）。🖼 指標カード1枚。

**S16 — パイプライン全体図（0:評価設計 から）**
- **0:評価設計（指標・閾値・評価セット）** → 1:前処理 → 2:増強 → 3:SFT → 4:GRPO → 5:評価。評価が全体を挟む形。
- 🖼 「NeMo一式 ↔ ローカル等価」対応表（Curator→datatrove/pandas、合成→distilabel/API、NeMo-RL→Unsloth、Eval→lm-eval-harness）。

**S17 — 環境: ローカル中心＋学習だけ借りる**
- **Macで前処理・評価・軽い推論（Ollama/MLX）**。学習(SFT+GRPO)だけ **Colab A100 / EC2 spot(g6e=L40S 48GB)**。予算$100以内。🖼 ローカル⇄借りGPUの境界図。

**S18 — ツール選定**
- **Unsloth**（単機最速・Colab配布・GRPO対応）を主役。GUI派は LLaMA-Factory。
- NeMo-RL は「**同じGRPOをデータセンター規模でやる本番ルート**」として1枚紹介。

**S19 — モデル選定: Qwen3.5-9B（主役）**
- 学習がColab/EC2なので手元GPUに縛られず**パラメータを増やせる**。
- **Qwen3.5-9B**: Apache 2.0、小型ながら日本語が非常に強い（公称で10倍規模級に匹敵する場面も／Gemma 3 12B超）。bf16 LoRA ~22GB(目安)、GRPOはUnslothで可(vLLM高速推論を切りUnsloth推論を使う条件)。借りGPU（A100/L40S）に収まる。
- **Qwen3.5-4B**: 反復・配布用の軽量版（~10GB）。（発展）27B はA100 80GBで。
- 思考デフォルトOFFで前回のthinking暴走を回避。注意: 最新transformers必須・T4で遅い→ColabはA100。Qwen3.5はVLMで**現状Ollama配信不可**(llama.cpp/vLLMで配信)。

**S20 — 【構築①】データ（質>量で役割別に選定）**
- 主役=**合成タスクデータ**（ダミー問い合わせをSonnetで「カテゴリ＋抽出項目」にラベル付け）。土台=**官公庁公開情報の自前収集/EDINET（商用可）** 少量高品質（※JaFInはCC BY-NC-SAで商用不可）。汎用維持=一般日本語instructionを少量。
- コンプラ: 実データ学習は先方OK後。ライセンスは Apache/MIT/CC-BY 優先、NC・NDは避ける。評価ベンチ(pfmt/fin-harness)は**評価専用**。

**S21 — 【構築②】増強（データを増やす）**
- 「データを増やす」＝**タスクに沿った合成**。Sonnetでラベル付き例を生成（蒸留の素）。品質管理＝スキーマ検証・重複排除・人手スポットチェック。
- 原則: 「**質 > 量、タスク適合 > コーパスの有名さ**」。エビデンス: 規模拡大・ドメイン適応は精度を確実には上げない（2026/2の日本語金融ベンチ）。

**S22 — 【構築③】SFT（教師ありファインチューニング）**
- Qwen3.5-9Bにタスクを教える（Unsloth/LoRA）。土台づくり。終わったら**即evalで base→SFT の差分を確認**。

**S23 — 【構築④】GRPO（グループ相対方策最適化）**
- 報酬 = **カテゴリ一致 ＋ 項目F1 ＋ スキーマ妥当性**（すべて検証可能＝RLVR）。
- **報酬は評価指標の一部、評価セットは報酬と分離**（reward hacking検出）。学習中に inference health check（空応答/反復検出）を挟む。

**S24 — 再現性の作り込み**
- チェックポイント → S3/Drive。spot中断前提の設計（Adam reset対策）。"連続学習≠分割学習"を踏まえた区切り方。

**S25 — 【評価＝山場】base vs SFT vs SFT+GRPO**
- S15で決めた指標・閾値に向けて階段状の改善を提示。前回「−35%」と対比、合格ラインを越える瞬間を見せる。🎬 同じ入力に対する3モデルの出力＆スコアを横並び。

**S26 — なぜ今回は"評価地獄"が起きないか**
- 正解と突合するだけ＝LLM審判ノイズ無し・0点トラップ無し。**評価ファーストで base から測っている** ＝「今回は動く」の技術的裏付け。

**S27 — 配布**
- 参加者に**軽量な4B版Colabノートブック**を配る → 手元でも回せる（本番デモは9B、配布は4B）。

**S28 — 第1回まとめ＆予告**
- 「失敗 → 評価ファースト → 動くモデル」まで到達。後編は「使う」＝アプリ組み込み＋コストに天井。

**S3 — 通しアーク図（右半分）** · 今日は「アプリ組み込み＆コストキャップ」。

**S4 — 課題設定: なぜローカルか**
- 裏目標: **コストをキャップ**。金融では加えて**データが社外(API)に出ない**＝モデルリスク管理(MRM)上も効く。

**S5 — 全体アーキ図** · ユーザ → LiteLLM →（ローカル小〜中モデル / Claude）＋ RAG ＋ Langfuse(可観測)。🖼 1枚絵。

**S7 — 【組み込み②】LiteLLMでOpenAI互換API化** · 前回資産を再利用。model_listにローカルとClaudeを併載。

**S8 — 【RAG（検索拡張生成）】社内ドキュメントQ&A**
- ベクタストアは**社内設置**＝データが外に出ない。知識は外付けなので、小〜中モデルでも「その文書には正確」を作りやすい。

**S9 — RAGの作法** · 根拠提示・社内の言い回し。軽いSFTで整える（GRPOを主役にしない理由＝採点が曖昧）。

**S10 — 【評価ファースト②】RAGの評価指標を先に決める**
- 検索=**Recall@k / MRR**、生成=**忠実性(Faithfulness)**・回答関連性・正確性、根拠=引用ソース正確率、健全性=「分かりません」率。
- **金融では忠実性が最重要**。gold回答＋gold出典の eval-set を最初に用意。ツール: RAGAS / Langfuse。🖼 RAG指標カード。

**S11 — 【ルーティング＝肝】LiteLLMで振り分け**
- 定型・高頻度 → ローカル(≒0円)、難しい尾 → Claude。これでClaude課金に**天井**。

**S12 — 振り分けの設計** · 何を"易"とみなすか（カテゴリ／信頼度／分類器）。フォールバックと安全弁。

**S13 — 【可視化＝山場】Langfuseでコスト内訳**
- ローカル/Claudeの比率＋コスト＋**Claudeエスカレーション率**を可視化。「同じ問い合わせ群でAPI課金がここまで下がる」。🎬 ダッシュボード。

**S14 — コストキャップの考え方** · 自己ホスト＝固定費、APIは尾だけ。break-evenの直感（量が増えるほど効く）。

**S15 — 品質と安全（正直スライド）** · ローカルの限界（汎用はSonnetに及ばない）を明言 → **だからハイブリッド**。

**S16 — 金融コンプラ** · 実データ学習は先方OK後。PII。MRM・継続モニタリング・モデル検証。

**S17 — 対象アプリへの応用像** · 分類/抽出（前回モデル）＋ RAG Q&A ＋ ルーティングの合わせ技。

**S18 — 運用・永続化と継続評価** · LiteLLM/Ollamaの常駐、監視、**評価の継続(continuous eval)** ＝指標を運用後もダッシュボードで追う。

## 第3回「守る」── 商用で生成AIを安全に運用する（ガードレール＆ゲートウェイ）

**ねらい**: 第2回で作ったRAG＋ルーティング構成を、商用（対象アプリ・金融）に耐える形にする。プロンプトインジェクション・データ漏洩・出力事故を、多層防御とゲートウェイ監視で抑える。
**山場**: 攻撃クエリ（直接＋RAG経由の間接インジェクション）を実際に投げ、ゲートウェイが入力/取得/出力の各レールで止め、Langfuseに発火が記録される様子。

**S1 — タイトル** · 「ローカルLLMを守る（後編の続き：守る）」／サブ「商用ガードレールとAIゲートウェイ」

**S2 — なぜ"守る"が要るか**
- 商用＝対象アプリ・金融。**事故1回で信頼が壊れる**。デモ品質 ≠ 本番品質。第1・2回で作った"動くもの"を、出してよいものにする回。

**S3 — 通しアーク（三部作の右端）** · 作る → 使う → **守る**。

**S4 — 脅威モデル：OWASP LLM Top 10（2025）から本アプリに効くもの**
- LLM01 プロンプトインジェクション（最重要）／LLM02 機微情報漏洩／LLM05 出力ハンドリング不備／LLM07 システムプロンプト漏洩／LLM08 ベクトル/埋め込みの弱点（RAG汚染）。🖼 6項目に絞った脅威マップ。

**S5 — プロンプトインジェクション①直接**
- ユーザー入力で「前の指示を無視して」等でシステムプロンプトを上書き／ロール変更／機密抽出。

**S6 — プロンプトインジェクション②間接（本アプリ最大の急所）**
- **RAGで取り込んだ文書に命令が埋め込まれる**攻撃。Gmail取り込みの偽レポート/コラムに指示文を仕込む攻撃面が現実に存在。**「RAGだけでは間接インジェクションを防げない」**（研究で確認）→ 取得レールが必須。

**S7 — 多層防御の全体像（ゲートウェイ図）**
- 入力レール → **AIゲートウェイ(LiteLLM)** → クエリ解析 → 取得レール(RAGチャンク検査) → 回答生成 → 出力レール → 監視(Langfuse)。🖼 1枚絵。**単一ツールでは10項目を網羅できない＝2〜3個を重ねる**。

**S8 — AIゲートウェイ＝LiteLLM（既存資産）**
- 全トラフィックの関所。pre/post hookでガードレールを差し込み、**全I/OをLangfuseに記録＝監査証跡**。「生成AIとのやり取りを監視するゲートウェイ」がこれ。

**S9 — 入力レール**
- ジェイルブレイク/インジェクション検知（**Llama Guard / Prompt Guard**）、**PII検知・マスク（Presidio）**、トピック/スコープ強制（市場レポート以外は断る）。第一防衛線＝悪い入力はLLMに渡す前に弾く。

**S10 — 取得レール（RAG固有・S6への解）**
- 取得したチャンク内の命令文を検出・サニタイズ、**データと命令の境界を明示（信頼境界）**。間接インジェクションはここで止める。取り込み時のチェック（LLM08対策）も併用。

**S11 — 出力レール**
- **忠実性ゲート（既存 `source_exists` ＝ 作話は事故）**、PII漏洩、**システムプロンプト/ペルソナ漏洩（執筆者スタイル(persona)＝商用IPの保護）**、スキーマ妥当性、下流（UI/SQL）への危険出力サニタイズ。

**S12 — ツール選定（役割分担で重ねる）**
- **NeMo Guardrails（NVIDIA, 5レール: 入力/対話/取得/実行/出力, Colang）** ← NVIDIAの世界が"守る"でも続く／**Llama Guard（8B・1Bでオンデバイス）**／**LLM Guard（入出力スキャナ）**／**Presidio（PII）**／**Guardrails AI（構造化出力）**。1つで全部やらない。

**S13 — ローカルで動かす意味**
- Llama Guard / Presidio を**自前GPUで動かす → 検査するデータも社外に出ない**（金融MRMの一貫性）＋ あなたのローカル資源に"守る"という追加の仕事。

**S14 — 監視＝Langfuse（既存資産）**
- ガードレール発火をスコア化・時系列で追う・アラート・低スコアtraceの調査＝**SIEMライト**。第2回のコスト可視化と同じ画面でセキュリティも見える。

**S15 — レッドチーミング/評価（評価ファーストをセキュリティへ）**
- promptfoo / garak で攻撃カタログをCIに組み込み、**防御も"先に評価"**。インジェクション成功率・PII漏洩率・忠実性違反率を指標化。

**S16 — レイテンシ予算**
- 高速分類器 10〜50ms vs LLM審判 200〜1000ms。同期ゲートは体感遅延に直結（10秒目標）→ **何を同期で止め、何を非同期監視に回すか**を設計。

**S17 — 正直スライド**
- **完全なインジェクション防御は不可能**。多層＋監視＋最小権限で"確率を下げ、起きたら検知・記録する"。残存リスクは受容してMRMに記録。

**S18 — 金融コンプラ統合**
- MRM・監査・データ最小化を、OWASP LLM Top 10 / NIST AI RMF / MITRE ATLAS に対応づけて整理。商用提案資料の骨にもなる。

**S19 — まとめ** · 「作る → 使う → 守る」。デモ品質から、**商用に出せる品質**へ。

**S20 — 次の一歩 / Q&A**
- 将来エージェント化（ツール実行）すると LLM06 過大な権限が効いてくる。継続的レッドチーミング、ガードレールのバージョン管理。

## 付録A: 用語集（正式名称）

| 略 | 正式名称 | 概要 |
|---|---|---|
| SFT | Supervised Fine-Tuning（教師ありFT） | 入力→正解出力で模倣学習 |
| LoRA | Low-Rank Adaptation | 小さな差分行列だけ学習する省メモリ手法 |
| EOS | End Of Sequence（系列終端トークン） | 応答終わりを示す特別トークン。壊れると生成が止まらない |
| GRPO | Group Relative Policy Optimization | 複数回答を相対比較して良い回答を強めるRL。DeepSeek-R1で有名 |
| RLVR | Reinforcement Learning with Verifiable Rewards | 正解と機械照合して報酬を決めるGRPOの使い方 |
| RAG | Retrieval-Augmented Generation | 外部文書を検索して回答に使う |

## 付録B: 評価指標まとめ（合格閾値は例 / タスクで調整）

**モデル（分類・抽出）**: 分類=Macro-F1≥0.85 ／ 抽出=フィールドF1≥0.90・レコードEM≥0.80 ／ 形式=スキーマ妥当率100% ／ 健全性=ループ・空応答率0% ／ 運用=レイテンシp50/p95・1,000件コスト。比較は base/SFT/SFT+GRPO 同一ホールドアウト。
**RAG**: 検索=Recall@5≥0.90・MRR ／ 生成=忠実性≥0.95・回答関連性・正確性 ／ 根拠=引用ソース正確率 ／ 健全性=「分かりません」率 ／ 運用=レイテンシ・コスト・エスカレーション率。
**原則**: 評価セットは学習データ・GRPO報酬と分離（reward hacking／リーク防止）。

## 付録C: 数字・エビデンス（Q&A用 / 要自己検証）

- **前回失敗**: base 0.534 → FT(v1) 0.182（−35%）。v2は test 全件0.000（inference破壊）。
- **GRPOの狭タスク実例**: Qwen-1.5B + GRPO ≈ o1（AIME）。
- **モデル(Qwen3.5, bf16 LoRA VRAM目安)**: 4B≈10GB / 9B≈22GB / 27B≈56GB。Apache 2.0。
- **GRPOのメモリ**: 同等SFTの約1.5〜2倍が一般則だが、Unsloth実装では大幅軽量（8B GRPOで約14〜18GB）。
- **借りGPU料金目安**: AWS spot g6e.xl(L40S 48GB) ≈ $0.6〜0.9/h、Colab A100 ≈ $1.5/h相当。一周20〜40 GPU時間で $15〜75 → $100以内。
- **「質>量」の裏付け**: 2026/2の日本語金融ベンチで、規模拡大・ドメイン適応は精度を確実には改善しないと報告。
