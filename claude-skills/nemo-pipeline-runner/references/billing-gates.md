# 課金承認ゲートの運用ルール（loop8-10の実績に基づく）

## 原則

1. **課金を伴う操作は事前に概算を提示し、ユーザー承認を得てから実行**（GPU起動・学習・教師API）
2. **「概算→小規模実測→再見積り→本走承認」の2段ゲート**を踏む。設計時の概算は外れるものとして扱い、
   本走の承認は必ず実測レートで取り直す
3. 実費はループ総括レポートに記録し、累計を更新する

## ゲートの型（loop10で確立したパターン）

| ゲート | 内容 | 規模感 |
|---|---|---|
| 設計承認 | plan doc に概算レンジを明記して PR | $0 |
| ゲートA: 配管検証 | 数step〜dryの実機で throughput（tps）・搭載可否・配管の生死を実測 | $5-10 |
| ゲートB: 本走 | 実測tps → 1ep時間 → `時間 × $4/h（g6e.12xlarge spot目安）` で再見積りして承認 | 数十$ |
| ゲートC: 評価API | 教師生成・judge・verify の件数×単価を提示して承認 | $3-10 |

見積り計算例（loop10 P4）: 実測 1,076 tps × 4GPU、コーパス 68.2M tok → 1ep ≈ 17.6h → ~$70（実費$75）。

## 実績（見積り精度のキャリブレーション用）

| ループ | 見積り | 実費 | 超過主因 |
|---|---|---|---|
| loop8 | — | ~$11 | OOMデバッグ空振り（colocated 9B GRPOは仕様外と判明） |
| loop9 | $100-170 | ~$200 | SFT 2回失敗＋GRPO 2ラウンド（＝手法選択ミスの再走） |
| loop10 | $40-80 | ~$98 | P4のデバッグ再走（mlflow/NCCL）込み |
| 累計 | — | **~$320**（2026-08時点） | |

**教訓: 超過の主因は常に「実機デバッグの再走」**。対策は
(a) デバッグを配管検証フェーズ（ゲートA）に閉じ込め、本走前に新規要素を全部踏んでおく
(b) 手法選択を decision-table.md で先に検証する（loop9の$100超過は選択ミス由来）
(c) 長走前にディスク・残プロセスを確認する（operations.md — ディスクフルはハング→再走の原因）

## API課金の保護（再課金ゼロの再開）

- 教師生成・judge・verify は**逐次ログ（追記jsonl）**にし、中断・再実行時は既判定を再利用する
  （loop9: クレジット切れ・API上限を跨いでも再課金ゼロで完走）
- 分割の再配分は既存 verified 件数以内に収めれば新規API呼び出しなしで $0 再ビルドできる

## 途中で止まった/失敗したときの判断

- 学習が走り出した後の一過性エラー（NCCL タイムアウト等）は、dmesg・ディスクを確認して
  ハード起因でなければ再走を提案（追加コストを明示）。走行中のものは原則完走させてから評価
  （途中止め→再走の方が高くつく）
- 評価が全滅でも**実測結果として総括レポート化する**（負の結果も成果。loop10の結論はそれ自体が運用知）
