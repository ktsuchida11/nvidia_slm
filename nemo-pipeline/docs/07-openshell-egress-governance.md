# 07. OpenShell（エージェント・セキュリティ／出口ガバナンス）— 補完レイヤの設計

> 位置づけ：**任意・将来検討**。NeMo Guardrails（会話レール）の代替ではなく、**インフラ層の補完**。
> クローズド網・金融ドメインでの「出口ポリシー＋認証情報分離＋監査」に効く。現状はアルファ版のため本線には載せない。

## OpenShell とは（正確に）
NVIDIA Agent Toolkit / NemoClaw の一部で、**自律AIエージェント向けのセキュア・ランタイム**。
モデルやアプリではなく **環境（インフラ）層でポリシーを強制**し、その強制は **プロセス外**で行う
（エージェント自身はガードレールを上書きできない）。3要素：
1. **サンドボックス**：エージェントごとに隔離コンテナ。長時間・自己進化型エージェント向け。
2. **ポリシーエンジン**：宣言的YAMLで filesystem / network / process / **推論ルーティング** を制御。
3. **privacy router（ゲートウェイ）**：全外向き接続を横取りし「許可／推論用ルーティング（呼び出し元の
   認証情報を除去しバックエンド認証情報を注入）／拒否＋ログ」。**機微コンテキストをローカルに留める**。
- k9s風の端末ダッシュボードでゲートウェイ／サンドボックスを**監視**。エージェント非依存・モデル非依存。
- 内部的には **単一Dockerコンテナ内の K3s(Kubernetes)** として動作。

## NeMo Guardrails と OpenShell の違い（補完関係）
| | NeMo Guardrails（本パイプラインで採用済み） | OpenShell（本書・任意） |
|---|---|---|
| 層 | **会話／アプリ層**（入力・取得・出力レール） | **インフラ／環境層**（プロセス外で強制） |
| 守る対象 | プロンプトインジェクション・PII・スコープ・忠実性 | 出口(ネットワーク)・認証情報・実行(プロセス/FS)・推論の行き先 |
| 主用途 | LLMの**入出力内容**を検査・遮断 | エージェントの**行動と通信**をポリシーで封じ込め＋監査 |
| 成熟度 | 実運用可 | **アルファ（single-player・粗削り）** |
→ **二層防御**：会話の中身は Guardrails、通信/実行/認証情報は OpenShell。役割が重ならず併用が自然。

## この案件でのフィット
### 今（RAGアシスタント＝非エージェント）
- 主な価値は **privacy router / 出口ポリシー**：全LLM・外部呼び出しを**単一の出口**に集約し、
  宛先allowlist・認証情報の分離・拒否＋ログを**アプリの外側**で強制。**クローズド網の徹底**に効く。
- LiteLLMとの違い：LiteLLM=ルーティング/フォールバック（アプリ内）。OpenShell=**ポリシー強制の出口**＋
  認証情報分離＋監査（アプリ外・プロセス外）。**併用可**（LiteLLMの外側にOpenShellの出口を置く）。
### 将来（ツール実行・エージェント化）
- Nemotronはツール呼び出し対応。RAGアシスタントが**行動する**（DB更新・外部API・コード実行）方向に進むと、
  サンドボックス＋プロセス/FS/ネットワークのポリシー強制が本領を発揮。ここで OpenShell が主役級になる。

## どこに差し込むか（設計）
```
[アプリ/LiteLLM] → ★OpenShell 出口ゲートウェイ（allowlist/認証情報分離/拒否+ログ）→ 外部LLM/ツール
                              └ privacy router：機微コンテキストはローカルモデルに留める
   ＋ 端末ダッシュボードで監視、YAMLポリシーで宣言的に管理、監査ログを Langfuse/SIEM へ
```
既存の「守る（S7）」に**出口ガバナンス**を一段足すイメージ。会話レール（Guardrails）はそのまま。

## 導入方針（現実的に）
1. **今**：本設計を置き、NeMo Guardrails は予定どおり採用。OpenShell は **PoC/スパイクで評価**（本線に載せない）。
2. **評価観点**：出口allowlist・認証情報分離・privacy routerのローカル保持・監査ログ・K3s(in Docker)の運用負荷。
3. **採用判断**：(a)アプリがエージェント化する (b)出口の集中管理／認証情報分離が要件化する、時に本採用。
4. **注意**：アルファ・single-player・マルチテナントは未提供。**本番クリティカルパスに置かない**。
   また K3s を伴うため、これまでの「K8s不要」方針の**例外**（この補完層だけK3s in Docker）と明記して扱う。
