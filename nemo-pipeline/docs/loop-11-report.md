## 3. 設計判断（なぜこの形か）

- **SKILL.md は判断フローだけを持ち、知識は references/ に分割** — スキル本体は毎回コンテキストに
  載る。全部入りにすると1周ごとに固定費を払うことになるので、**必要になったときだけ読ませる**構成にした
- **loop report が正、references/ は蒸留版** — 矛盾したら `docs/loop-XX-report.md` を優先する、と
  SKILL.md に明記。二重管理は必ずズレるので、どちらが正かを先に決めた
- **失敗を根拠として書く** — 意思決定表の各行に「なぜそう判断するか」の実測を紐づけた。
  一般論だけの表は次の周で無視される
- **未消化コンポーネントは手順化せず、題材として温存** — S7 Guardrails と NeMo Retriever は
  SKILL.md の消化状況表に「未実機検証 / 未消化」と**明示だけ**して、実行手順は書かなかった
  （やっていないことを手順として書くと、エージェントが動く前提で走ってしまう）

## 6. 運用の学び

- **測定を伴わないループもレポートを書く。** 書かなかったことで、後続4ループの参照先が3週間欠番になった。
  「何を決め、何を後回しにし、その理由は何か」は数字がなくても記録価値がある
- **計画（`loop-XX-plan.md`）も作っていない。** スコープ5点はチャット上の合意だけで進めた。
  PR本文に残っていたので復元できたが、これは運任せ
- **ドキュメントの配布物は、リポジトリの更新と同期しない限り必ず腐る。** 書き戻しを4回やっても、
  `cp -r` を1回も再実行しなければ効果はゼロ。手順の最後に「配布先へ反映」を置く
- 番号の欠番は**それ自体がバグの兆候**として機能した（整合性チェックが機械的に検出できた）
