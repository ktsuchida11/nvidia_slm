# ループ12 レポート — NeMo Retriever（RAG）vs DAPT知識注入の費用対効果（総括）

期間: 2026-08-08（設計〜本走を1日で完了）。計画: docs/loop-12-plan.md（PR #60）。実装: PR #61。

## 1. 問いと答え

**問い**: その知識は本当に重みに入れる必要があるか？ — DAPT知識注入（loop10で完全同点・
多epoch路線の見積り $300-550）に対し、RAG（検索で文書を渡す）はいくらで何点取れるか。

**答え**: **RAGの圧勝で、DAPT多epoch知識注入路線はクローズ。** closed-book 0.0402（base=dapt10）が、
全量20万チャンクからの検索+文脈注入だけで **0.4724（11.8倍）** になった。重みは一切変えていないので
忘却リスクはゼロ、文書更新はインデックス追記のみ。実費は本ループGPU合計 **~$12**（教師API $0）。

| 判定軸 | 物差し | 結果 |
| --- | --- | --- |
| ① 検索品質 | recall@5 / MRR（gold doc_id・n=199・プール2,530文書） | ✅ **recall@5 0.6985 / recall@1 0.4975 / MRR 0.5827**（目標0.7にSE±0.033内で到達） |
| ② 生成品質（RAGの階段） | RAG probe正解率 vs closed-book 0.0402 | ✅ **0.4724**（成功基準 ≥0.4 を超過。SE±0.035） |
| ③ 非退行 | — | 原理的に不要（重み不変・評価時のみ文脈注入。設計書§5どおり省略） |

## 2. 実測サマリ（P2小規模 → P3全量の対比）

| 指標 | P2: probe 50文書プール（4,153チャンク） | P3: 全量2,530文書（202,318チャンク） |
| --- | --- | --- |
| recall@1 / @5 / @10 | 0.7839 / 0.8945 / 0.9347 | 0.4975 / 0.6985 / 0.7387 |
| MRR | 0.8333 | 0.5827 |
| RAG probe_acc | **0.6432** | **0.4724** |
| gold_in_ctx_rate | 0.8894 | 0.6985 |

- embedding: NeMo Retriever NIM `llama-3.2-nv-embedqa-1b-v2`（L40S用TRT FP8プロファイル・**dim 2048**。
  設計時想定1024の2倍でベクトル1.66GB — フラット総当たりで依然問題なし）
- gold_in_ctx_rate = recall@5 が両プールで一致 → 検索→文脈投入の配管は無損失
- プール50倍（検索難度増）で recall@5 は 0.894→0.699、正解率は 0.643→0.472。
  gold文脈があるときの読解正答率は両プールとも **~68-72%** で安定（正解率の律速は検索と読解の積）

### 誤答の内訳（①②分離設計の成果）

199問の落ち方: **検索ミス 30%**（gold_in_ctx=0）+ **読解ミス 23pp**（goldを渡しても誤答:
gold_in_ctx=1 の32%）。次の一手が指標から直接決まる:

- 検索側: recall@10 0.7387 なので top10→5 の rerank 改善余地は +4pp どまり。効かせるなら
  検索k=100からの rerank NIM か、チャンク整形・クエリ拡張
- 読解側: grounded QA SFT（RAG文脈前提の抽出読解の形式学習）で ~23pp の伸びしろ — **loop13 の最有力候補**

## 4. 実機の罠カタログ（NIM初導入で4件）

| # | 罠 | 対処 |
| --- | --- | --- |
| 1 | nvcr.io から NIM イメージ pull が「Access Denied」 | `docker login nvcr.io -u '$oauthtoken' --password-stdin` に NGC_API_KEY を渡す（ユーザー名は文字列 `$oauthtoken` そのもの。旧ログインキャッシュは NIM リポジトリに無効） |
| 2 | NIM 起動直後に死ぬ: manifest download「Permission denied (os error 13)」 | キャッシュマウント `~/.cache/nim` を docker が root 所有で自動作成 ↔ NIM は非root(uid 1000)。`sudo chown -R 1000:1000 ~/.cache/nim`。`--rm` 併用だとログごと消えるのでフォアグラウンド再現が早い |
| 3 | NIM 稼働中に vLLM が起動不能: 「Free memory 40.48/44.39 GiB < utilization 0.92」が**どのGPUでも**出る | `--gpus all` の NIM は Triton の CUDA pool を全GPUに確保（~4GB×4枚）。同居時は**両サービスとも** `GPU='--gpus device=N'` で別GPUにピン留め（Makefile 変数上書きで対応可） |
| 4 | tmux 内で埋め込みAPIに「Name or service not known」 | `tmux new` は新シェル = 外で取った `EMB_IP` が消えて URL のホスト名が空になる。IP取得は tmux セッション内で行う |

副産物の実測: NIM は L40S 用 TRT FP8 プロファイルを自動選択。202,318チャンク（8,924万字）の
埋め込みは 1GPU で完走、インデックスは EBS の `/data/retriever` に残置（loop13 で再利用可）。

## 5. 運用の学び

- **P2で新規要素を全部踏む設計が機能した**: NIM pull・権限・GPU同居・tmux の4罠はすべて
  50文書の小規模フェーズで顕在化し、全量フェーズはノーエラー1発完走（超過主因「実機デバッグ再走」を回避）
- 中断再開設計（vectors.f32 追記+meta整合ガード）は SSM タイムアウト2回をまたいで機能
- コスト: ゲートA+B合算 ~3h・~$12 で計画枠 $12-24 の下限着地。教師API $0（probe QA 199問を再利用）
