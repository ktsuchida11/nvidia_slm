# ループ14 総括 — rerank NIM: probe 0.6332 到達・「文脈は量より質」の実証・次の律速は埋め込み検索の取りこぼし

実施: 2026-08-27（実機評価1セッション）。設計: docs/loop-14-plan.md（PR #70）。実装: PR #71。
実行手順: docs/loop-14-runbook.md。学習なし・教師APIなしの推論オンリーのループ。

## 1. 問いと答え

**問い**: 埋め込み検索を k0=50-100 で広く取り、rerank NIM（llama-3.2-nv-rerankqa-1b-v2）で
top5 に絞れば、プロンプト長を増やさず gold_in_ctx 率と probe_acc が伸びるか？

| 構成（全て sft13 アダプタ・rag199 n=199） | probe_acc | gold_in_ctx_rate | gold_in_k0_rate |
| --- | --- | --- | --- |
| k=5（loop13 ベースライン） | 0.5075 | 0.6985 | — |
| k=10（rerank なしの k 拡大） | 0.5427 | 0.7387 | — |
| rerank k0=50 → top5 | 0.5879 | 0.7186 | 0.7889 |
| rerank k0=100 → top5 | **0.6131** ✅（判定値 ≥0.55） | **0.7588** ✅（判定値 ≥0.75） | 0.8342 |
| rerank k0=100 → top10 | **0.6332**（歴代最高） | 0.7638 | 0.8342 |

**答え**: 伸びる。両判定値をクリアし、closed-book 0.0402 から始まった RAG の階段は
**0.6332（15.7倍）**に到達。k=5 比 +12.6pp、k=10 比 +9.1pp。

## 2. 分かったこと（3つの実証）

1. **文脈は量より質**: rerank top5（gold_in_ctx 0.7186）が k=10（同 0.7387）を正答率で上回った
   （0.5879 > 0.5427）。gold の同梱率が低くてもノイズの少ない文脈の方が読解精度が出る —
   「k を増やせば良い」への反証
2. **rerank の変換効率は 91% で安定**: gold が k0 候補内にあれば、k0=50 でも 100 でも約91%を
   top5 に引き上げる（0.7186/0.7889 ≒ 0.7588/0.8342）。k0 拡大の利得がそのまま通る
3. **次の律速が定量化された**: **16.6% は gold が top100 にすら入らない** = rerank では原理的に
   救えない埋め込み検索そのものの取りこぼし。gold_in_k0_rate（本ループで追加した計測）が
   このボトルネック切り分けを1指標で可能にした

レイテンシ実測感: 埋め込み検索の k0 拡大はほぼ無料（行列積 top-k のみ）。増分は rerank 1回
（100パッセージ交差採点で1問 +0.5〜1秒）で、生成 4〜6秒に対し1〜2割の上乗せ。
オフライン/社内QAでは明確に割に合う。対話UIでは k0 がチューニングノブ。

## 3. 実機の罠（新規1件）

- **NGC_API_KEY が空のシェルで NIM を起動すると「静かに」死ぬ**: `docker login` の
  「password is empty」が唯一の兆候。イメージ pull は旧ログインキャッシュで通ってしまい、
  コンテナは起動直後にモデル取得失敗で死に `--rm` が痕跡ごと消す（`docker logs` 不能）。
  対処: 起動前に `echo ${NGC_API_KEY:+OK}` で確認 + 初回はフォアグラウンド起動で失敗を見える化
- 既知罠の再確認: GPU ピン留め（embed=0 / vLLM=1 / rerank=2 で Free memory 衝突なし）、
  ブリッジ IP の tmux 内再取得 — いずれも runbook 化で回避
