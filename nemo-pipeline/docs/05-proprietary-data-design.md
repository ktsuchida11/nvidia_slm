# 05. 独自データ取込の設計（設計のみ・将来実装用）

> 現状は公開・合成データのみ。将来「自社の文書・ログ・ナレッジ」を学習に使う時に備え、
> **安全に取り込む仕組みの骨だけ**を先に定義する（コードは未実装、プラグ位置と規約を確定）。

## 0. 方針
- 独自データは価値が高い一方、**PII・機密・規制・権利**のリスクを伴う。
- そこで既存パイプラインの手前に **「S1' データ取込・ガバナンス」ステージ** を1枚差し込む。
- 原則：**承認されるまで学習に流さない** / **レッドラインは絶対に学習しない** / **来歴を必ず残す**。

## 1. 位置づけ（既存パイプラインへのプラグ）
```
[独自文書/ログ] → ★S1' 取込・ガバナンス → S1 収集・管理 → S2 蒸留 → S4/S5 学習 → S6 → S7
                    （新設・設計のみ）        （既存の重複排除/PII/ライセンスゲートを再利用）
```
S1' は既存の **ライセンスゲート＋PIIマスク＋メタ付与** を土台に、承認・分類・用途制御を足したもの。

## 2. S1' の構成要素（設計）
| # | 要素 | 内容 | 既存資産との関係 |
|---|---|---|---|
| 1 | **取込マニフェスト（データ契約）** | 1ソース1枚。出所・権利・同意・PII・機微度・用途・保持を記述 | `templates/source_manifest.yaml` |
| 2 | **承認ワークフロー（人手ゲート）** | `approved:true` になるまで後段に渡さない | 川幡さん等が承認者。CI/スクリプトで検査 |
| 3 | **分類** | sensitivity / contains_pii / secrets を判定・付与 | s1_curateのPII検知を拡張 |
| 4 | **レッドライン強制** | 顧客PII(マスク不能)/認証情報/規制・NDA は **never**（学習除外） | 新規ルール |
| 5 | **用途ラベル** | train / eval / rag-only / never を各レコードの `meta.allowed_use` に | record.schemaで型化済 |
| 6 | **来歴・系譜（PROV-O）** | 取込者・版・checksum・変換履歴を記録 | Croissant-RAIで機械可読化 |
| 7 | **保持・削除（忘れられる権利）** | 保持期間・削除手順・オプトアウトを運用 | manifestのretention |
| 8 | **アクセス制御・監査** | 誰がいつ取り込み/学習に使ったかを記録 | Langfuse/監査ログ |

## 3. データ分類 → 許可用途（決定表）
| 機微度＼PII | PIIなし | マスク可 | マスク不能 |
|---|---|---|---|
| public | train | train | (該当しない) |
| internal | train | train（マスク後） | rag-only / never |
| confidential | eval or rag-only | rag-only | **never** |
| restricted(規制/NDA) | **never** | **never** | **never** |

→ 「学習(train)に入れてよいか」を機械的に決められる。**trainに満たない多くの社内資料は rag-only が受け皿**（§7）。neverはRAG検索用にすら使わない。

## 4. 実装の段階（将来）
1. **今（設計のみ）**：本ドキュメント＋テンプレート（manifest/record.schema/data card）を配置。運用規約を合意。
2. **最初の独自ソースが来たら**：`s0b_intake/` を新設し、manifest検証＋承認チェック＋分類＋用途ラベル付与を実装
   （s1_curateのライセンス/PII関数を流用）。出力は既存の `/data/raw` 形式＋richメタ。
3. **拡大期**：Croissant-RAIで来歴/許諾を機械可読化し、監査を自動化。削除要求への対応フローを整備。

## 5. レッドライン（絶対に学習に入れない）
- 顧客・従業員の個人情報でマスク不能なもの / 認証情報・秘密鍵・トークン
- 契約・NDA・規制（個人情報保護法/GDPR等）で学習利用が制限されるデータ
- 出所・権利が不明なデータ（unknownライセンスはゲートで既に拒否）

## 6. 最小の受け入れ基準（S1'を通す条件）
- [ ] source_manifest.yaml があり `approver.approved: true`
- [ ] license が商用可（S1ゲート通過）／ consent の根拠あり
- [ ] PII は none か masked（present は不可）
- [ ] 各レコードに `allowed_use` が付与され、train対象がレッドラインに触れない
- [ ] 来歴（provenance）と checksum が記録されている

## 7. rag-only データの扱い（独自データ活用の"入口"）

ビジネスには「**学習させたくないが、回答時には参照したい社内資料**」が大量にある
（社内規程・手順書・製品仕様・過去回答・議事録・顧客別の設定など）。これらは学習(train)に入れず、
**RAGの検索対象としてのみ使う** = `allowed_use: [rag-only]` として扱う。ここが独自データ活用の最も安全な第一歩。

### なぜ rag-only から始めるのが良いか
- **"忘れさせられない"問題が起きない**：学習に混ぜたデータはモデルから抜けない。RAGなら**索引から消せば即反映**
  （削除要求・オプトアウト・情報の陳腐化・契約終了にそのまま対応できる）。
- **回答時にアクセス制御を効かせられる**：誰がどの資料を引けるかを**クエリ時点で権限判定**でき、
  機微資料を「見てよい人にだけ」提示できる（学習では不可能な粒度）。
- **出典を明示できる**：既存の `source_exists` ゲートがそのまま効き、社内資料に基づく回答の根拠を示せる（MRM/監査向き）。
- **導入障壁が低い**：モデル改変不要。索引に入れるだけで始められ、効果測定・撤収も容易。

### rag-only 固有のリスクと対策（学習しないから安全、ではない）
| リスク | 対策（既存資産との対応） |
|---|---|
| 間接プロンプトインジェクション（取込資料に命令が埋め込まれる） | **取得レール**（S7）でチャンク内命令を検出・サニタイズ・信頼境界 |
| 権限跨ぎの情報漏洩（他者専用資料の内容が回答経由で漏れる） | **取得時アクセス制御**：クエリのユーザ権限で検索対象をフィルタ（下記） |
| PII/機微情報が回答に出る | 学習しなくても**出力レールのPIIチェック**は必須（S7出力レール） |
| 古い/誤った社内資料を根拠にする | 索引の鮮度管理・バージョン・失効フラグ。`source_exists`＋人手レビュー |
| 索引の汚染（誰でも書き込めると攻撃面） | 取込は S1' の承認ゲート経由に限定（manifest必須） |

### 取得時アクセス制御（設計）
- 各ドキュメント/チャンクに **`acl`（閲覧可能なロール/グループ）** をメタとして付与。
- 検索は「ユーザの権限 ∩ ドキュメントのacl」でフィルタしてから上位kを返す（**ベクトル検索の前後で権限適用**）。
- 監査：誰が・いつ・どの資料を根拠に回答を得たかを記録（Langfuse/監査ログ）。

### rag-only を通すための最小要件（S1'の一部）
- [ ] source_manifest.yaml があり `approved: true`（学習と同じ承認ゲート）
- [ ] `allowed_use: [rag-only]`（train を含まない）
- [ ] PII は none / masked、または **acl で閲覧範囲を限定**
- [ ] レッドライン（規制・NDA・マスク不能PII）は rag-only でも扱わないか、厳格なacl＋監査
- [ ] チャンクに acl・source・version・license を付与（record.schema の meta を流用）

### 昇格パス（rag-only → train）
将来その資料を学習にも使いたくなったら、**改めて学習用の承認**を取り、PII除去・匿名化・ライセンス確認を経て
`allowed_use` に `train` を追加する（決定表§3で train 可の区分に入ることが条件）。
rag-only での運用実績（アクセス制御・出典・鮮度）がそのまま学習投入の判断材料になる。

> まとめ：**まず rag-only で安全に社内資料を"使い倒し"、価値と運用が固まったものだけを慎重に学習へ昇格**する。
> これが独自データ活用の現実的な順序。
